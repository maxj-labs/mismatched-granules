Proposal for Zarr, Icechunk and VirtualiZarr

One array from granules that don't match

Many NASA collections cannot be virtualized into a single Zarr array because their files change compression, chunk shape or chunk boundaries partway through the record. Three small, separable changes fix this. They were built and checked on seven collections, and every read matched the source files.

The problem is common, and it comes in three forms

A Zarr array has one chunk grid, one codec chain and one fill value. Archives written over twenty years do not. Sampling the most-used collections that carry a virtualizability blocker shows three recurring causes.

Mechanism one: a position-based switch codec

The array stays an ordinary Zarr array with one manifest entry per source chunk, on a rectilinear grid. Its single codec holds a short table of cases, run-length encoded along the joined axis. Each case names:

  • a codec chain, the granules' own;
  • an encoded chunk shape, when chunks are stored larger than their cell (HDF5 stores a granule's last chunk whole), so the codec decodes then crops;
  • a fill value, only when the granules leave chunks unwritten and their HDF5 fill differs from the array's.

Nothing is stored per chunk. In every collection tested the table had one or two cases and zarr.json stayed under 1.4 KB.

"codecs": [{
  "name": "switch",
  "configuration": {
    "axis": 0,
    "cases": [
      { "chunks": 25550,
        "codecs": [bytes, zlib],
        "encoded_chunk_shape": [null, 231, 364] },

Daymet Puerto Rico, 1950–2025: 27,740 daily chunks, two cases.

The one thing it needs from zarr-python. A codec is not told which chunk it is decoding. The prototype reads the grid position back out of the store key, which works and is a hack. Passing the chunk's coordinates to codecs (the same request made for other reasons in zarr-specs#399) removes it.

Mechanism two: virtual shards

When the chunk shape changes, no chunk grid fits both layouts, rectilinear or not. The answer is to make each Zarr chunk a shard sized to a common multiple of the layouts, holding either era's source chunks. The shard is never written. Its reference is a concatenation, and zarr's existing sharding_indexed codec reads it by byte range.

What Icechunk needs. A virtual reference that is a literal prefix followed by several byte ranges of one object, and that answers a ranged read by fetching only the parts the range touches. The prototype stores both in the reserved ChunkRef.extra field, so the manifest schema is unchanged. The diff is 193 lines of Rust plus two arguments on VirtualChunkSpec.

A per-chunk header, as proposed in NASA-IMPACT/veda-odd#498, is the special case of one literal and one range. Building the general form costs little more and unlocks the case headers cannot reach.

Virtual shards cost the same as plain chunks, once range merging is off

Requests reaching the source, relative to reading the same selection chunk by chunk · Daymet North America, 2019–2021

Virtual shards, zarr defaultsVirtual shards, range merging offThe axis line is 1.0×: the chunk-by-chunk baseline

zarr merges byte ranges of a shard that lie within 1 MiB of each other. In a virtual shard, neighbours in the layout are separate source chunks, so merging fetches chunks nobody asked for. Setting sharding_coalesce_max_gap_bytes to 0 removes the over-read; bytes fetched follow the same pattern (164.5 MB against 54.2 MB for the series).

Why this and not the alternatives

Against array concatenation

It works everywhere and needs no store change, and it was the first thing built. But the joined array reports one chunk spanning everything, so xarray's default is a single 9.3 GB dask chunk; every reader must reimplement it; and manifest operations do not compose with it. Virtual shards now cover the one case only it could handle.

Against headers for everything

A header per chunk is the right tool when parameters truly vary per chunk. For era-style changes it stores 27,740 copies of two values and needs a store format change, for no measured gain. It also does not compose with partial reads of a shard, because the header shifts every offset.

Where headers still win. The position table grows by one case per run. A collection where every granule needs its own parameters (an odd-length OCO-2 granule, a GPM granule with unwritten chunks and its own fill value) would get a case per granule. That is the point at which per-chunk context in the manifest is the better tool, and the Icechunk change proposed here already provides it.

Limits of this evidence

Not yet measured

  • S3 in us-west-2. Source requests were counted against a local HTTP server; timings are local.
  • Full records. Each collection is 2 to 6 granules and one or two variables. MODIS-Aqua chlorophyll has a third layout that was not tested.
  • Data type changes between granules.
  • Shards whose source chunks sit in more than one file. The Icechunk prototype references one object per shard.

Known gaps in the prototypes

  • The Icechunk branch has no tests of its own and the Rust test suite was not run.
  • Parts of a multi-range reference are fetched one after another, so a whole-shard read was slower under latency (7.8 s against 5.4 s for a full map).
  • Per-granule fill values were tested on synthetic files only (1,200 of 5,760 cells wrong before, 0 after). No real sample left chunks unwritten.
  • Icechunk 2.3.1 split every chunk fetch over HTTP into five requests, even 26 KB chunks. Not investigated; it affects every approach equally.
