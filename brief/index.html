Real Collections and Virtual Shards

The other pages compare options on small test files and Daymet. This page holds what was learned from real NASA granules: how seven collections disagree, whether a layout table can join them, how virtual shards handle a change of chunk shape, and what Zarr, Icechunk and VirtualiZarr would each have to take on.

How real collections disagree

A Zarr array has one chunk grid, one set of codecs and one fill value. Archives written over twenty years do not. Among widely used collections graded as hard to virtualize, three causes recur: the compression changes, chunks are padded or cut short at the end of a granule, or the chunk shape itself changes.

Change points were located by binary search over each record using metadata-only range requests (14–15 probes per collection). The collections were picked from 86 graded for virtualizability, by public access counts and by whether a few granules could be downloaded. They are not a random sample. “Crop” means the codec decodes a chunk stored larger than its place in the grid and cuts it to size.

What the layout table holds

The array stays an ordinary Zarr array with one reference per source chunk, on a rectilinear grid. Its single codec holds a short table of layouts. Each layout names:

  • the codecs the granules were written with, plus a cast_value where a granule stores another data type;
  • an encoded chunk shape, when chunks are stored larger than their place in the grid (HDF5 stores a granule's last chunk whole), so the codec decodes and then crops;
  • a fill value, only when granules leave chunks unwritten and their fill value differs from the array's.

A granule that lacks the variable is a run of chunks that stores nothing. In every collection sampled the table had one to three layouts and zarr.json stayed under 1.9 KB.

Virtual shards: when the chunk shape changes

When the chunk shape changes, no chunk grid fits both layouts. The answer is to make each Zarr chunk a shard: a larger block, sized to a common multiple of the two chunk shapes, that holds the source chunks of either era. The shard is never written. Its reference lists a small index followed by the byte ranges of the source chunks, and Zarr's existing sharding_indexed codec reads it by byte range.

What Icechunk needs. A virtual reference that is a literal followed by several byte ranges, from one object or several, and that answers a ranged read by fetching only the parts the range touches, concurrently. The branch stores this in the reserved ChunkRef.extra field, so the flatbuffer schema is unchanged. A key in front of each chunk, as the keyed designs on the other pages use, is the special case of one literal and one range.

Virtual shards make the same requests as plain chunks, once range merging is off

Requests reaching the source, relative to reading the same selection chunk by chunk · Daymet North America, 2019–2021

Virtual shards, zarr's default range mergingVirtual shards as the planner writes them (no merging)Bars start at zero; 1.00× is the chunk-by-chunk baseline

zarr-python merges byte ranges of a shard that lie within 1 MiB of each other. In a virtual shard, neighbours in the layout are separate source chunks, so merging fetches chunks nobody asked for. The planner turns merging off in each layout, so readers need no setting. With parts fetched concurrently, a whole-grid map took 2.8 s from shards against 4.8 s chunk by chunk, at 20 ms per request.

Open issues and limits

Design questions these prototypes do not settle

  • A new codec in every reader. Any Zarr implementation that wants these arrays must implement the codec. It does no I/O of its own except through sharding, but it depends on the rectilinear chunk grid, which zarr-python still gates behind a setting.
  • Codecs that depend on position. Finding the layout by position means zarr-python must pass chunk coordinates to the codec, and such a codec breaks when chunks are re-keyed or nested inside another codec. A key in each reference avoids this, at the price of the Icechunk change.
  • Writing. By position the codec can encode, so these arrays can be written through Zarr. By key it is read-only: nothing tells the codec which layout a new chunk belongs to.
  • Appending. Appending along the joined axis works when the new granules fit the existing grid or shards. Writing by region, or appending a layout that does not fit, means planning the array again.
  • Older Icechunk readers. A reference with a literal or further ranges is stored without a location, so a reader that predates the change fails with an error and cannot return wrong bytes. Whether that suffices, or a format version bump is wanted, is for Icechunk to decide.
  • Checksums. A timestamp checksum is applied to every object a reference reads. An ETag still covers the first object only.
  • Names. switch is also the name of the header-based codec in refkv PR #73. One of them should change.

Limits of the evidence

  • Only zarr-python reads these arrays. No other Zarr implementation was tried.
  • Nothing was measured against S3. Source requests were counted at a local HTTP server.
  • Records are complete for Daymet only. MODIS-Aqua and OMPS are samples across their records; GPM, ATL08, TEMPO and OCO-2 are a few granules each.
  • Shards that span a whole map make large manifests: MODIS-Aqua needs about 60 KB per day, most of it the shard index.
  • Per-granule fill values and data type changes were tested on constructed files only. No real sample had unwritten chunks with a differing fill value.
  • A “no data” marker that changes between granules can be remapped, but real data equal to the array's marker would then be masked.
  • xarray's default dask chunks follow the Zarr chunks: 27,740 small ones for Daymet Puerto Rico, 360 MB shards for North America. Neither is a good default.
  • The codec decodes chunks one at a time, which costs a fraction of a millisecond per chunk more than a plain array. A network request hides that; local reads of very small chunks would show it.
