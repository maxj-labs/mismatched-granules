Proposal for Zarr, Icechunk and VirtualiZarr

One array from granules that don't match

Many NASA collections cannot be virtualized into a single Zarr array because their files change compression, chunk shape or chunk boundaries partway through the record. Three separable changes fix this. They are built as prototype branches and were checked on seven collections: every read matched the source files.

Max Jones, Development Seed · 10 November 2026 · Experiments and write-up prepared with Claude Code. Code: maxj-labs/mismatched-granules. These are prototypes, not pull requests; the open issues are listed at the end.

The problem is common, and it comes in three forms

A Zarr array has one chunk grid, one codec chain and one fill value. Archives written over twenty years do not. Sampling the most-used collections that carry a virtualizability blocker shows three recurring causes: the codec changes, chunks are cut short at granule ends, or the chunk shape itself changes.

Change points were located by binary search over each record using metadata-only range requests (14–15 probes per collection). The collections were picked from 86 graded for virtualizability, by public access counts and by whether a few granules could be downloaded. They are not a random sample.

Mechanism one: a position-based switch codec

The array stays an ordinary Zarr array with one manifest entry per source chunk, on a rectilinear grid. Its single codec holds a short table of cases, run-length encoded along the joined axis. Each case names:

  • a codec chain, the granules' own, with a cast_value in front where a granule stores another data type;
  • an encoded chunk shape, when chunks are stored larger than their cell (HDF5 stores a granule's last chunk whole), so the codec decodes then crops;
  • a fill value, only when the granules leave chunks unwritten and their fill differs from the array's. A granule that lacks the variable is a run that stores nothing.

Nothing is stored per chunk. In every collection tested the table had one to three cases and zarr.json stayed under 1.9 KB.

What it needs from zarr-python. A codec is not told which chunk it is decoding. The branch adds that: a codec that sets needs_chunk_coords receives the chunk's grid coordinates in its ArraySpec. Without it the codec can still read the position back out of the store key, which is how it ran against released zarr-python as a plugin.

Mechanism two: virtual shards

When the chunk shape changes, no chunk grid fits both layouts, rectilinear or not. The answer is to make each Zarr chunk a shard sized to a common multiple of the layouts, holding either era's source chunks. The shard is never written. Its reference is a concatenation, and zarr's existing sharding_indexed codec reads it by byte range.

What Icechunk needs. A virtual reference that is a literal prefix followed by several byte ranges, of one object or of several, and that answers a ranged read by fetching only the parts the range touches, concurrently. The branch stores this in the reserved ChunkRef.extra field, so the flatbuffer schema is unchanged.

A per-chunk header, as proposed in NASA-IMPACT/veda-odd#498, is the special case of one literal and one range. Building the general form costs little more and reaches the case headers cannot.

Virtual shards cost the same as plain chunks, when ranges are not merged

Virtual shards, zarr's default range mergingVirtual shards as the planner writes them (no merging)Bars start at zero; 1.00× is the chunk-by-chunk baseline

zarr merges byte ranges of a shard that lie within 1 MiB of each other. In a virtual shard, neighbours in the layout are separate source chunks, so merging fetches chunks nobody asked for. The planner turns merging off per case, so readers need no setting. With parts fetched concurrently, a whole-grid map took 2.8 s from shards against 4.8 s chunk by chunk, at 20 ms per request.

The per-chunk mechanisms are interchangeable on speed

On Daymet Puerto Rico, 76 years, every way of telling the codec which chain applies was built and timed. They differ by less than matters; the choice should be made on what each one requires.

Why this and not the alternatives

Array concatenation as the main route

It works everywhere and needs no store change, and it remains the fallback when Icechunk cannot store a shard. Its array can now report chunks that line up with the pieces, so it no longer offers readers one giant chunk. What remains against it: every reader must implement a codec that reads other arrays, manifest operations do not compose with it, and editing a piece silently changes the joined array.

Headers for everything

A header per chunk is the right tool when parameters truly vary per chunk. For era-style changes it stores 27,740 copies of two values and needs a store format change, for no measured gain. It also does not compose with partial reads of a shard, because the header shifts every offset.

Where headers still win. The position table grows by one case per run. A collection where every granule needs its own parameters would get a case per granule. That is the point at which per-chunk context in the manifest is the better tool, and the Icechunk change proposed here already provides it.

The same tax applies to the switch codec. Any reader that wants these arrays must implement it, in every language. It is smaller than a concatenation codec and does no I/O of its own except through sharding, but it is still a new codec, and it depends on the rectilinear chunk grid, which zarr-python still gates behind a setting.

Open issues and limits

Design questions these prototypes do not settle

  • Older Icechunk readers. A reader that predates the change ignores ChunkRef.extra and would return a multi-part chunk without its prefix and further ranges: wrong bytes, no error. This needs a format flag or version bump before it could ship.
  • Checksums. A reference's ETag or timestamp covers its first object only. Parts in other objects are fetched unchecked.
  • Listing sources. Icechunk operations that enumerate virtual chunk locations do not yet see the locations of further ranges.
  • Codecs that depend on position. Passing chunk coordinates to a codec is the least composable option raised in zarr-specs#399. It is used here because it needs nothing from the store.
  • Appending. A planned array cannot be appended to or written by region yet, which forward-processing pipelines need.
  • Names. switch is also the name of the header-based codec in refkv PR #73. One of them should change.
  • Read-only. The switch codec has no encoder, so these arrays cannot be written through Zarr, and another implementation has nothing to test an encoder against.

Limits of the evidence

  • Only zarr-python reads these arrays. No other Zarr implementation was tried.
  • Nothing was measured against S3. Source requests were counted at a local HTTP server; timings are local.
  • Complete records for Daymet only. MODIS-Aqua and OMPS are samples across their records; GPM, ATL08, TEMPO and OCO-2 are a few granules each.
  • Manifest size for shards that span a whole map: MODIS-Aqua needs about 60 KB of manifest per day, most of it the shard index.
  • Per-granule fill values and data type changes are proven on constructed files. No real sample had unwritten chunks with a differing fill.
  • A marker for "no data" that changes between granules can be remapped, but real data equal to the array's marker would be masked.
  • xarray's default dask chunks follow the Zarr chunks: 27,740 small ones for Daymet Puerto Rico, 360 MB shards for North America. Neither is a good default.
