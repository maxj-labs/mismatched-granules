Every Option, Tested

The public discussions on joining mismatched granules into one Zarr array propose about sixteen options. Each was built or emulated here and run against the same ten small test cases. Subsets were then run against edits to a stored array, two worst cases and real Daymet granules.

Every mark and number, in the tables and in the text, is generated from result files in maxj-labs/mismatched-granules (eval/, results/eval/). Prepared with Claude. An earlier version of this page ranked the options; its tests were uneven, and this version replaces it.

What separates the options
Whether the array survives an edit to the store
Each edit changed only the references of the files involved. With a hashed key in each reference, all 58 trials read correctly when the file's layout was already in the table. By position, every edit that changed the number of chunks was refused until the table was rewritten, and 3 replaced-file trials read wrong values with no error.
What does not
Speed, among the seven layout-table options
On twelve years of Daymet Puerto Rico they made the same requests and took 30.0 to 30.8 s for a full time series. Raising zarr-python's concurrency brought all of them to about 3 s.
What each one needs
A store change, or a codec that is told the chunk's position
A key in the reference needs a new kind of Icechunk reference (a literal followed by byte ranges) and cannot be stored as Kerchunk references. Position needs neither, except where the chunk shape changes.

The options

Taken from zarr-specs#399 and #288, zarr-extensions#74 and PR #75, NASA-IMPACT/veda-odd#498, VirtualiZarr#1111 and refkv PR #73. Seven of them are the same codec. It holds a table of layouts (the discussions call them cases): the ways a chunk in this array can be stored. The seven differ only in how a reader learns which layout a chunk has. They share one planner and one encoding of the table, so differences between their rows come from that choice alone.

Virtual shards (d-v-b, zarr-specs#399) are not a row of their own. Every layout-table option uses them when the chunk shape changes, which is the “chunk shape change” test case below.

Proposed but not built:

  • A storage transformer (zarr-specs#399 design 2.3; a generalised transformer chain, mkitti). zarr-python refuses any array that declares one, so there is nothing to run it in.
  • An “array to files” codec (jbms). It ends the rule of one key per chunk, which Icechunk, VirtualiZarr and zarr-python all assume, and was too large a change to prototype here.
  • A union data type (d-v-b). It would let one array hold two data types, but does not address codecs, chunk shapes or padding.
  • Index transforms as in TensorStore (jbms). TensorStore cannot read virtual references, so only the cost of its stack driver on native arrays was measured (under Worst cases).

The test cases

  1. Codec eras. #399 case 1: gzip, then shuffle + gzip, then uncompressed.
  2. File lengths. #399 case 2: monthly files of 31, 28 and 31 days, each one chunk.
  3. Padded last chunk. #399 case 3: 10 steps in chunks of 4, the last chunk stored whole.
  4. Packing per file. #399 case 4: int16 with a scale_factor and add_offset of each file's own.
  5. Data types. #399 case 5: int16 files followed by float32 files.
  6. Chunk shape change. Chunk shape changes off the joined axis (Daymet North America in 2020).
  7. Fill value differs. Files leave chunks unwritten and declare different fill values.
  8. Variable absent. One file does not have the variable.
  9. Layouts alternate. Two layouts that alternate file by file, 12 files.
  10. Packing per chunk. Every chunk packed with its own scale and offset (as GRIB packs messages), 60 files.

Why an option cannot describe a test case

  • The conditional codec works on bytes. It can switch compressors, but it cannot crop a padded chunk, and it cannot change the data type, packing, chunk shape or fill value. Adding encoded chunk shapes fixes the cropping only.
  • Encoded chunk shapes and the declared valid domain deal with padding only. The array still has one set of codecs, one inner chunk shape and one fill value.
  • Copying the chunks that do not fit has nothing to keep when every file or chunk packs its values differently: all of the data would be copied.
  • open_mfdataset fills a file that lacks the variable with NaN. The stores return the fill value the other files declare, which is what this test expects.

Released software. Every codec-based option is refused with UnknownCodecError. The declared domain is the exception: an ordinary reader sees the padding as data and returns an array of the wrong shape with no error. The grid option, where it pads, is refused only by an unrelated reshape error.

New codecs, released Icechunk. Stores whose references carry a prefix or several ranges are refused with FormatError. Position reads in 9 of 10, because it needs the Icechunk change only where the chunk shape changes. The option where the store prepends an index is refused only by luck: released Icechunk returns the bytes with no index in front, and the codec happens to fail on what it takes for one.

Kerchunk references. The position and key options were also written as Kerchunk references and read through fsspec. Position read correctly in 9 of 10 test cases; the exception is the chunk-shape change. Key read in 0 of 10, because a Kerchunk reference is either inline bytes or one byte range, never a literal followed by a range. The other options were not tried.

Edits to a stored array

zarr-specs#399 asks that a solution keep working when a tool edits the manifest (that it “compose with manifest-level operations”). Seven kinds of edit were tested:

  • three drop chunks: the first chunk, the first file, or the last chunk;
  • three add a file: appended, inserted in the middle, or put at the front as a backfill;
  • one replaces a file with another of the same length.

Each edit changes only the chunk references of the files involved (including the key in front, for the keyed options) and updates nothing else: not a codec's configuration, a side array, a list of pieces or an attribute. A trial is one edit on one test case. Six of the ten test cases were used, and each option was run on those it can describe. A trial reads the whole array, each file's part on its own, and single cells. It is correct if every read equals the files, wrong if any read returns wrong values without an error, and refused if reads raise an error.

A key in the reference moves with the reference. With hashed 8-byte keys, with or without per-chunk numbers, every drop and every added or replaced file in a layout the array has read correctly. A file in a new layout is refused until that layout is added to the table, unless it differs only in numbers that the reference itself carries.

By position, edits are refused, not misread, with one exception. The codec checks that its table covers exactly the array's chunks, so any edit that adds or removes chunks fails when the array is opened, until the table is rewritten. That check was added during this work; without it, dropping leading chunks read wrong values in some test cases. The exception is replacing a file with one of the same length in a different layout. The chunk count is unchanged, so there is nothing to check, and 3 such trials read wrong values with no error. The option where the store prepends the chunk index has the same check and the same exception. Tables kept in side arrays or behind the emulated store call have no such check, and misread more often.

A 1-byte numbered key is not safe to edit. Adding a file at the front or in the middle, or replacing one, can change which number a layout has: 7 trials read wrong values with no error. A key that is a hash of the layout does not have the problem.

Keeping each file as its own array survived every edit tried. The reference-per-chunk codec read correctly in every trial, because nothing is shared between files. It cannot drop less than a whole file, and its costs are in the next section. The concatenation codec lists its pieces and checks that list against the array's shape, so it refuses every edit except replacement.

Caveats. Trial counts are small, in places two or three per cell. The store-context row is an emulation whose table is indexed by position; a store that kept the context with each reference would carry it along, and that was not tested. The grid rows keep encoded sizes in an attribute where the proposal puts them in the chunk grid. Renaming, concatenating two joined arrays, and nesting under another codec were not run. VirtualiZarr can only append so far, so these edits were made directly on the stored references.

Two sizes for metadata. “zarr.json” is the document a reader parses to open the array. “All metadata, stored” is everything the repository keeps apart from chunk data (snapshots and manifests, compressed). The two can differ by an order of magnitude, because a long table of similar layouts compresses well.

Where every chunk has numbers of its own, the options that carry those numbers with each chunk keep zarr.json under 1 KB. The options that can only name a layout need one layout per chunk: zarr.json grows to 6.0 MB or more, and opening the array takes 0.33 to 0.40 s. Once compressed in the repository the gap narrows: stored metadata runs from 252 KB to 850 KB across the layout-table options. This worst case varies exactly the two numbers that the per-chunk options carry, so it shows them at their best.

Where two layouts alternate, each layout is written once. zarr.json is under 1 KB for five of the options. For the two whose zarr.json lists which run of chunks has which layout (position, and the store-prepended index), it is 129 KB: a pair of integers per run. Stored metadata is 259 KB to 298 KB for all seven. A prefix in every reference does make manifests larger: 328 KB with a key and two numbers, against 168 KB by position, in the packed case.

Read time per chunk is the wall time to read everything divided by the number of chunks, with ten chunks in flight; it is not the cost of one chunk. The layout-table options took 0.51 to 0.67 ms in the alternating case and 1.07 to 5.98 ms in the packed one. The slow end of the packed range is the options with one layout per chunk (6.0 ms by position, 6.0 ms by key alone). With 16,000 distinct layouts the codec builds a new codec chain for nearly every chunk; the options that carry numbers per chunk took 1.1 to 1.4 ms.

Concatenation with one piece per chunk writes one array per piece, which is why its stored size and write time grow. Its read time per chunk also grows with the number of pieces (3×, 4×, 7× the key option's at 1,000, 4,000 and 16,000). That is probably my implementation and not the design: TensorStore's stack driver, given 16,000 one-chunk native arrays as layers, opened in 0.24 s and read everything at 0.03 ms per layer, from a 5.3 MB spec.

What this test can and cannot show. It shows that the options make the same requests, and that none adds a round trip. It cannot show small differences in decoding cost: at the default setting a full time series took about 69 ms per request with ten in flight, well above the server's 20 ms, so the test harness dominates and a millisecond per chunk is invisible.

The seven layout-table options stay close together. For the full Puerto Rico series they are within 3% of each other at the default setting and 12% with 120 in flight, which is inside the run-to-run noise. Concatenation matched them on Puerto Rico at the default setting, took 6.8 s against 3.0 s with 120 in flight, and made more requests on North America (475 against 439 for the series).

The reference-per-chunk codec looked 6× faster at the default setting, but only because it ran more requests at once. It reads each year through a nested array read, so twelve years ran together, each with ten chunks in flight. With 120 allowed for everyone it took 3.2 s, the same as the rest. On whole North America maps it was slower (4.7 s against 3.0 s) with the same requests.

zarr-python's concurrency setting changed these times by about 10×, far more than any choice between the options.

refkv as released (0.2.0, no Icechunk), on the same Puerto Rico files and server at the default setting, took 34.2 s for the whole series with 4,380 requests, and every read equalled the files.

Reading the results

The tests do not produce a single winner. They show two workable designs for the layout table, and a trade-off between them.

  • Put a key in each reference (a hashed key, with or without per-chunk numbers; with them it is refkv PR #73's design). Edits touch only the references that change, and a file in a layout missing from the table is refused. It needs Icechunk references that are a literal followed by byte ranges, which virtual shards also need. It cannot be stored as Kerchunk references, and its manifests are larger.
  • Find the layout from the chunk's position. It needs no store change unless the chunk shape changes, reads through released Icechunk and as Kerchunk references, and stores the least. Its table must be rewritten on every edit. A missed rewrite is refused, except for a replaced file of the same length, which can be misread silently.
  • If chunks carry numbers of their own (per-file or per-chunk packing), carrying those numbers with each chunk keeps zarr.json small. Three options did that: in the reference, in side arrays, and through a store call. Only the first also read correctly after the edits above.
  • Keeping files as separate arrays (concatenation, or a reference per chunk) describes everything and reads with released Icechunk once the codec is installed. Joined by reference it survived every edit; joined by a list it refused them. Its costs grow with the number of pieces, so it suits a few eras better than many small granules.
  • The narrow proposals each solve part of the problem and can be combined; two of them together covered 5 of the 10 test cases.

My reading, which the tests inform but do not settle: the deciding question is whether anything edits the store after it is built without also updating the layout table. If files are inserted, backfilled, replaced or dropped that way, the layout belongs in the reference. If the store is built once, or only appended to by a tool that rewrites the table, position is simpler and asks less of the store. The overview sets this beside a survey of how often NASA collections change away from the end.

Limits of this evaluation

  • Only zarr-python reads any of these arrays.
  • Timings are from one machine. Nothing ran against S3.
  • The ten test cases are small files written for this test. They show whether an option can describe a situation, not how common it is.
  • The fraction copied by the copying option reflects how the test cases were built: 20% for the padded case here, about 1.4% for a year of Daymet North America.
  • Daymet was run for ten options, the Kerchunk test for two, and the worst cases for eleven.
  • Two options are emulations, as marked in the first table: the store context call, and encoded chunk shapes in the grid. Real implementations could behave differently.
  • The conditional codec and the key-and-numbers codec are my implementations of others' designs. refkv itself was run only on Daymet Puerto Rico.
  • How the store knows to prepend an index is a stand-in (it reads a codec option); a real design needs a flag of its own.
  • For a file without the variable, the expected values are a convention: the fill value the other files declare.
