Every Option, Tested

The discussions on joining mismatched granules into one Zarr array propose about fifteen different mechanisms. Each was built or emulated and run against the same ten cases, the same requirements and the same real granules. This page reports what each one did.

The options

Taken from zarr-specs#399 and #288, zarr-extensions#74 and PR #75, NASA-IMPACT/veda-odd#498, VirtualiZarr#1111 and refkv PR #73. Seven of them are the same codec, a table of cases, and differ only in how a chunk's case is found; that is the question most of the threads argue about, so each way is tested separately.

Virtual shards (d-v-b, zarr-specs#399) are not a row of their own: every switch option uses them when the chunk shape changes, which is the “chunk shape change” case below.

Proposed but not built.

  • A storage transformer (zarr-specs#399 design 2.3; a generalised transformer chain, mkitti). zarr-python refuses any array that declares one, so there is nothing to run it in.
  • An “array to files” codec (jbms). It ends the rule of one key per chunk, which Icechunk, VirtualiZarr and zarr-python all assume. Too large a change to prototype here.
  • A union data type (d-v-b). It would let one array hold two data types; it does not address codecs, chunk shapes or padding, and the data-type case is handled by a cast in the chain.
  • Index transforms as in TensorStore (jbms). TensorStore cannot read virtual references, so its stack driver was only measured for cost on native arrays, below.

The cases

  1. Codec eras. #399 case 1: gzip, then shuffle + gzip, then uncompressed.
  2. File lengths. #399 case 2: monthly files of 31, 28 and 31 days, each one chunk.
  3. Padded last chunk. #399 case 3: 10 steps in chunks of 4, the last chunk stored whole.
  4. Packing per file. #399 case 4: int16 with a scale_factor and add_offset of each file's own.
  5. Data types. #399 case 5: int16 files followed by float32 files.
  6. Chunk shape change. Chunk shape changes off the joined axis (Daymet North America in 2020).
  7. Fill value differs. Files leave chunks unwritten and declare different fill values.
  8. Variable absent. One file does not have the variable.
  9. Layouts alternate. Two layouts that alternate file by file, 12 files.
  10. Packing per chunk. Every chunk packed with its own scale and offset (as GRIB packs messages), 60 files.

Why an option cannot describe a case

  • conditional codec, padded last chunk: chunks are stored larger than their place in the grid, and a bytes-to-bytes codec cannot crop.
  • conditional codec, packing per file, data types, packing per chunk: the files differ before the bytes stage (data type or packing), which a bytes-to-bytes codec cannot vary.
  • conditional codec, chunk shape change: the chunk shape changes, and a bytes-to-bytes codec cannot change what a chunk decodes to.
  • conditional codec, fill value differs: a bytes-to-bytes codec cannot give a run of chunks its own fill value.
  • Encoded chunk shapes in the grid, codec eras, packing per file, data types, layouts alternate, packing per chunk: the files' codec chains differ; a chunk grid with encoded chunk shapes keeps one chain for the array.
  • Encoded chunk shapes in the grid, chunk shape change: the chunk shape changes; a chunk grid with encoded chunk shapes keeps one codec chain and one inner chunk shape.
  • Encoded chunk shapes in the grid, fill value differs: the files' fill values differ; a chunk grid with encoded chunk shapes keeps one fill value.
  • Declared valid domain, codec eras, packing per file, data types, layouts alternate, packing per chunk: the files' codec chains differ; a declared domain keeps one chain for the array.
  • Declared valid domain, chunk shape change: the chunk shape changes; a declared domain keeps one codec chain and one inner chunk shape.
  • Declared valid domain, fill value differs: the files' fill values differ; a declared domain keeps one fill value.
  • Copy the chunks that do not fit, packing per file, packing per chunk: every file packs or narrows its values in its own way, so no file's chain can hold the others' values: all would be copied.
  • No store: open_mfdataset, variable absent: xarray fills the file that lacks the variable with NaN, where the stores return the fill value the other files declare.

Readers without the feature. Every store from the matrix was opened by released zarr-python 3.4.2. All the codec options are refused with UnknownCodecError. The declared domain is the exception: an ordinary reader sees the padding as data and returns an array of the wrong shape with no error. The grid option is refused only by an unrelated reshape error. A reader that has the codecs but released Icechunk refuses every store whose references carry a prefix or several ranges (FormatError), and reads the rest correctly.

Composition. The first chunks of each array were dropped the way a manifest tool would: shape and chunk grid shortened, references moved up, the codec's configuration untouched. Options that find the case from something stored with the chunk still read correctly. Options that find it from the chunk's position do not, and in the alternating-layout and packing cases they returned wrong values without an error. A store that kept the context with each reference would carry it along, which is how that row is emulated.

Without Icechunk. As Kerchunk references read through fsspec, position selection read correctly in 5 of 6 cases (the exception is the chunk-shape change, which needs virtual shards); key selection in 0 of 6, because a Kerchunk reference is either inline bytes or one byte range, never a literal followed by a range. Concatenation and the side-array option need only plain references. Key selection was also run on refkv as released, which has such references.

† by inspection of how the option stores its data, not by a run.

Growth of zarr.json from 1,000 to 4,000 to 16,000 chunks, every chunk packed its own way: by position 375 KB → 1.5 MB → 6.0 MB; by key 386 KB → 1.5 MB → 6.2 MB; key + parameters 921 B → 921 B → 923 B; store context 871 B → 871 B → 873 B.

Only two options keep zarr.json flat when every chunk has parameters of its own: carrying the numbers in each reference, and a store that returns them as context. A plain key, like position, then needs one case per chunk. The 1-byte case number stops at 256 cases.

Concatenation with one piece per chunk writes one array per piece, which is what makes its manifests and build time grow. TensorStore's stack driver, with 16,000 one-chunk native arrays as layers: a 5.3 MB spec (334 bytes per layer), 0.24 s to open, 0.03 ms per layer to read everything. That is the cost of the general design when the layers are native arrays; it says nothing about virtual ones.

The seven ways of finding the case do not differ on speed. They fetch the same chunks and take the same time to within a few percent, on both datasets. Concatenation matched them on Puerto Rico and made slightly more requests on North America (475 against 439 for the series). The reference-per-chunk codec is the outlier in both directions: faster on the Puerto Rico series, for the reason below, and slower on whole North America maps (4.7 s against 2.8 s) with the same requests.

One apparent winner was an artefact. The reference-per-chunk codec read the Puerto Rico series in 5.0 s against 29.9 s. It reads each year through a nested array read, so twelve years ran at once, each with zarr-python's default of ten chunks in flight. With that setting raised to 120 for everyone, position took 3.1 s, key 3.2 s, reference 3.2 s and concatenation 6.8 s. zarr-python's concurrency setting moves these reads by about 10×, far more than any choice between the options.

refkv as released (0.2.0, no Icechunk), on the same Puerto Rico files and server: 34.2 s for the whole series with 4,380 requests, every read equal to the files.

What this changes

The earlier brief suggested shipping position selection first and adding key selection later. These results support a different emphasis.

  • Carry the case with the chunk. A key in each reference, followed by any per-chunk numbers, was the only virtual design that described all ten cases, composed with a manifest operation as it stood, and stayed small in both worst cases. This is refkv PR #73's design. It depends on references that are a literal followed by byte ranges, which the Icechunk branch adds and which virtual shards need anyway.
  • Treat position as the route that needs no store change, not as the foundation. It reads through released Icechunk and through Kerchunk references. Its table must be rewritten by every tool that reorders chunks, and a tool that does not know to do so can produce silently wrong data.
  • A store context call would be as good on these tests. It matched key + parameters wherever it was run, but only as an emulation: it needs a new store method, a spec change and a place in the manifest, none of which exist.
  • Keep concatenation as the fallback. It describes everything and needs nothing from the store. Its costs grow with the number of pieces, not chunks, so it is cheap for a few eras and expensive for many small granules.
  • The narrow options are narrow. conditional described 4 of 10 cases; encoded chunk shapes in the grid and a declared domain 3; copying the chunks that do not fit 8, storing half or more of the data again in five of them.

One gap closed along the way: key selection could not give a run of unwritten chunks its own fill value, because such chunks have no reference. They are now stored as the key alone, and the fill-value case passes.

Limits of this evaluation

  • Three options are emulations, as marked in the first table: the store that prepends an index, the store context call, and encoded chunk shapes in the grid. An implementation inside Icechunk or zarr-python could behave differently, especially on speed.
  • The conditional codec and the key + parameters codec are my implementations of others' designs. refkv itself was run only on Daymet Puerto Rico.
  • Only zarr-python reads any of these arrays.
  • The ten cases are small files written for this test. They show whether an option can describe a situation, not how common the situation is.
  • The composition test is one operation. Renaming an array, concatenating two joined arrays and nesting under another codec were not run.
  • Timings are from one machine against a local HTTP server. Nothing ran against S3.
