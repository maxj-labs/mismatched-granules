One Zarr Array from Granules That Disagree

Many archives of netCDF and HDF5 granules cannot be virtualized as one Zarr array, because the files change compression, chunk shape, data type or fill value partway through the record. This site tests the fixes proposed for Zarr, Icechunk and VirtualiZarr, and says which to choose for which kind of archive.

Work in progress, prepared with Claude, revised 13 November 2026. Only zarr-python reads these arrays, the test records are small, and nothing has been run against S3.

The problem, in one example

Daymet publishes one netCDF file per year. Until 2019 each day's chunk was compressed one way; from 2020 a shuffle filter was added. A Zarr array has one codec chain for all its chunks, so the years cannot be presented as a single array without copying the data. The proposed fixes all let one array hold chunks encoded in more than one way. They differ in how a reader finds out which way a given chunk was encoded.

Two places to keep that answer

In the array's metadata, by position

chunks 0–2: layout A  ·  chunks 3–5: layout B
201720182019202020212022

The array records which run of chunks uses which layout. Nothing is stored with the chunks. It needs no change to the store unless the chunk shape changes, and it can be written as Kerchunk references.

With each chunk, as a key in its reference

layouts: A, B
A2017A2018A2019B2020B2021B2022

Each chunk's reference begins with a few bytes naming its layout. The key goes wherever the reference goes. It needs Icechunk references that are a literal followed by byte ranges, which exist only on a branch, and it cannot be written as Kerchunk references.

Both are one codec holding a table of layouts. A different route keeps arrays apart and joins them: one array per file, joined by reference (each chunk of the joined array is a pointer to a file's own array), or one array per run of like files, joined by a list in the joining array's codec. These need nothing new from the store, and every reader needs a codec that opens other arrays.

What happens when the store is edited

All four read every test case correctly when the array is built in one go. They part ways when a store is edited afterwards. Each edit below was made by a writer that adds, removes or replaces chunk references, in whatever form the design gives a reference, and rewrites nothing the array already has: not the table, not the list, not another file's references.

By position, every edit that adds or removes chunks is refused until the table is rewritten. The codec checks that its table covers the array's chunks and raises when it does not; that check was added during this work, and without it some of these edits read wrong values. One edit it cannot detect: a file replaced by another of the same length in a different layout. All 3 of the 3 trials where the layouts differed read wrong values with no error.

By key, nothing needs rewriting unless a layout is new. A file in a layout the array already has can be appended, inserted, backfilled or swapped in. A file in a new layout needs one entry added to the table, and reads are refused until it is. The writer does have to put the key in each new reference, so it is not ignorant of the design; what it need not do is touch anything already stored.

One array per file never needs anything rewritten, because each file keeps its own metadata. It pays for that elsewhere: with 16,000 one-chunk files it stored 19× as much beside the chunk data as the keyed design and took 11× as long to write, and nothing smaller than a whole file can be dropped.

Each trial reads the whole array, each file's part on its own, and single cells (24 reads); it counts as correct only if every read equals the files, and as wrong if any read returns wrong values silently. Trials are the test cases each design can describe. A file that changes how the others must be described (a different fill value, data type or chunk shape) forces the array to be planned again in the table designs: 3 of 3 such trials were refused by key. Keys here are 8-byte hashes of the layout; 1-byte numbered keys are not safe to edit this way (7 of 40 trials read wrong values). Full results: Every Option, Tested.

How often do NASA records receive data away from the end?

If records only ever grew at the end, edits would be rare. To see, 26 collections were examined through NASA's public metadata catalogue: the seven surveyed earlier in this project and nineteen other well-known ones, chosen by me. For each granule the catalogue gives the time its data covers and the time its file was produced. In 7 of 26 collections, at least 1% of the files produced in the last year of the sample hold data more than 30 days older than data already produced. 4 more show only short delays, a few days of latency between tiles or passes. 6 show older data being made earlier in their record but not in the last year, typically a reprocessing campaign. 9 show nothing behind, and for 8 of those the sample could not have shown it, for the reason given in the table.

This is what public metadata suggests, not a record of what any store experienced. Production time is whatever the provider reports; it is not the time a file was published, and some providers reset it when files are migrated. Only current files are seen, so a file replaced in data order leaves no trace. “Behind” is measured against the newest data produced so far, so the first filling of a new version, done newest-first, counts as behind throughout. Files made within a day of each other are treated as one delivery. Collections with more than 60,000 granules are sampled from their newest data only. The last year of production is the last in the sample, whenever that was. A store built once, after a reprocessing campaign has finished, would see none of that campaign.

What to choose

After the store is built, will files be inserted, backfilled, replaced or dropped by anything other than a tool that rewrites the design's own table?

  • If not, finding the case by position is enough and asks the least. It needs no store change where the chunk shape is stable, and it read correctly as Kerchunk references in 9 of 10 test cases. VirtualiZarr's append rewrites the table as it goes; that path is covered by its tests.
  • If so, keep the case in each reference. Edits then touch only the references that change, a new layout that is not registered is refused loudly, and a replaced file cannot be misread. The price is the Icechunk change and somewhat larger manifests (76.4 KB against 62.4 KB for twelve years of Daymet Puerto Rico).
  • If the chunk shape changes (Daymet North America in 2020), the Icechunk change is needed either way, because each Zarr chunk becomes a virtual shard. That removes most of position's advantage.
  • If every file or chunk has numbers of its own (packing with its own scale and offset), carry those numbers in the reference beside the key, as refkv PR #73 does.
  • If the files are few and large and edits are frequent, one array per file is the most forgiving, at the costs above.

Speed did not separate the table designs in these tests. On twelve years of Daymet Puerto Rico, behind a local server adding 20 ms per request, the seven variants read a full series in 30 to 31 s with the same requests, and in about 3 s once zarr-python was allowed more requests in flight.
