One Zarr Array from Granules That Disagree

Archives of netCDF and HDF5 granules often cannot be virtualized as one Zarr array, because the files change compression, chunk shape, data type or fill value partway through the record. This site collects prototypes of the proposed fixes and the evidence for choosing between them.

Work in progress, prepared with Claude. Only zarr-python reads these arrays, and nothing has been run against S3.

The original proposal

One Array from Mismatched Granules

The case for a switch codec and for virtual shards, with results from Daymet and six other NASA collections. Written before the full evaluation; where the two disagree, the evaluation is right.

For Icechunk, Zarr and VirtualiZarr developers.

What the evaluation found

  • No single winner. Two designs for a table of cases both work, and trade against each other.
  • Keeping a chunk's case in its reference was the only kind that kept reading correctly when a tool dropped leading chunks without knowing the codec. It needs Icechunk references that are a literal followed by byte ranges, and cannot be stored as Kerchunk references.
  • Finding the case from the chunk's position needs no store change where the chunk shape is stable, but its table must be rewritten whenever leading chunks move; where it was not, reads failed or, in some cases, returned wrong values with no error.
  • Array concatenation describes everything and reads with released Icechunk, at a cost that grows with the number of pieces.
  • The case-table options did not differ on speed. zarr-python's concurrency setting changed read times far more than the choice between them.
