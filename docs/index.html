One Zarr Array from Granules That Disagree

Many archives of netCDF and HDF5 granules cannot be virtualized as one Zarr array, because the files change compression, chunk shape, data type or fill value partway through the record. This site tests the fixes proposed for Zarr, Icechunk and VirtualiZarr, and says which to choose for which kind of archive.

Work in progress, prepared with Claude, revised 13 November 2026. Only zarr-python reads these arrays, the test records are small, and nothing has been run against S3.

The problem, in one example#

Daymet publishes one netCDF file per year. Through 2019 each day's chunk was compressed one way; from 2020 a shuffle filter was added. A Zarr array applies the same codecs to every chunk, so the years cannot be presented as a single array without copying the data.

Every proposed fix lets one array hold chunks stored in more than one layout: a combination of compression, chunk shape, data type and fill value. The fixes differ in how a reader learns which layout a given chunk has.

Two places to keep that answer#

In the array's metadata, by position#

chunks 0–2: layout A  ·  chunks 3–5: layout B
201720182019202020212022

The array's metadata lists which run of chunks has which layout. Nothing is stored with the chunks. Released Icechunk can hold it unless the chunk shape changes, and so can Kerchunk references.

With each chunk, as a key in its reference#

layouts: A, B
A2017A2018A2019B2020B2021B2022

Each chunk's reference starts with a few bytes naming its layout, so the key moves wherever the reference moves. It needs a new kind of Icechunk reference (a literal followed by byte ranges), which exists only on a branch, and it cannot be written as Kerchunk references.

Both of these are a single new codec that holds a table of layouts. The alternative is to leave the files as separate arrays and join them, which needs nothing new from the store but a codec that opens other arrays. Two forms were tested:

  • One array per file, joined by reference. Each chunk of the joined array points to one file's array.
  • One array per run of files with the same layout, joined by a list. The joined array's metadata lists the pieces in order.

What happens when the store is edited#

All four designs read every test case correctly when the array is built in one go. They differ once the store is edited. Each edit below changes only the chunk references of the files involved and updates nothing else: not the table of layouts, and not the list of pieces. That is what a general-purpose tool that does not know the design would do.

By position, any edit that adds or removes chunks is refused until the table is rewritten. The codec checks that its table covers exactly the array's chunks and raises an error when it does not. The one edit it cannot catch is a file replaced by another of the same length in a different layout: all 3 such trials read wrong values with no error.

By key, nothing is rewritten unless a layout is new. A file in a layout the array already has can be appended, inserted, backfilled or swapped in. A file in a new layout needs one entry added to the table, and reads raise an error until it is added. The writer must still put the right key in each new reference; it never touches what is already stored.

One array per file never needs anything rewritten, because each file keeps its own metadata. The cost shows up elsewhere: with 16,000 one-chunk files it stored 19× as much metadata as the keyed design and took 11× as long to write. It also cannot drop anything smaller than a whole file.

A trial is one edit applied to one test case. It makes 24 reads (the whole array, each file's part, and single cells) and counts as correct only if every read equals the source files. Keys are 8-byte hashes of the layout; 1-byte numbered keys are not safe to edit (7 of 40 trials read wrong values). A new file that changes how the existing files must be described (a different fill value, data type or chunk shape) means planning the array again in both table designs. Full results: Every Option, Tested.

See it happen#

examples/reproduce.py writes six chunks in two layouts, then makes two edits. It is 72 lines, runs in memory and needs only the zarr-python branch. The two layouts differ only in byte order and nothing is compressed, so a chunk read with the wrong layout cannot fail to decode: the worst case for a silent error.

How often do NASA records change away from the end?#

If records only ever grew at the end, appending would be the only edit that matters. To check, I looked at 26 collections in NASA's public metadata catalogue (CMR): the seven sampled for Real Collections and Virtual Shards and nineteen other well-known ones that I chose. For each file the catalogue gives the time its data covers and the time the file was produced. A file is late when it was produced at least a day after a file holding newer data. In 7 of 26 collections, at least 1% of the files produced in the sample's last year were more than 30 days late. 4 more show only short delays, a few days between tiles or passes. 6 have late files earlier in their record but not in the last year, typically from a reprocessing campaign. 9 show no late files, but for 8 of those the sample could not have shown any, for the reason in bold in the table.

This is inferred from public metadata; it is not a record of what any store experienced. Production time is whatever the provider reports, which is not the time a file was published, and some providers reset it when files are migrated. Only current files are visible, so a file that was replaced leaves no trace. When a new version of a collection is first filled in, newest data first, every file counts as late. Collections with more than 60,000 files are sampled from their newest data only. A store built once, after a reprocessing campaign has finished, would see none of that campaign.

What to choose#

After the store is built, will anything insert, backfill, replace or drop files without also rewriting the array's table of layouts?

  • If not, finding the layout by position is enough and asks the least. It needs no store change while the chunk shape is stable, and it read correctly as Kerchunk references in 9 of 10 test cases. VirtualiZarr's append rewrites the table as it goes.
  • If so, put a key in each reference. Edits then touch only the references that change, a file in an unknown layout raises an error, and a replaced file cannot be misread. The price is the Icechunk change and somewhat larger manifests (76.4 KB against 62.4 KB for twelve years of Daymet Puerto Rico).
  • If the chunk shape changes (Daymet North America in 2020), the Icechunk change is needed either way, because each Zarr chunk becomes a virtual shard. Position then loses most of its advantage.
  • If every file or chunk has numbers of its own (its own scale and offset, say), carry those numbers in the reference beside the key, as refkv PR #73 does.
  • If the files are few and large and edits are frequent, one array per file is the most forgiving, at the costs above.

Speed does not decide it. On twelve years of Daymet Puerto Rico, behind a local server adding 20 ms per request, all seven variants of the layout table made the same requests and read a full time series in 30 to 31 s, or about 3 s once zarr-python was allowed more requests in flight.
